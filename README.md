# VINCODE_TRAIN

차량 유리에 부착된 **VIN 코드 스티커**를 탐지하는 YOLO 모델의 학습 파이프라인.

현장 카메라 영상 → 프레임 선별·정제 → 반자동 라벨링 → 세션 단위 분할 → 학습 → 평가까지의
전 과정을 스크립트로 재현할 수 있게 정리한 저장소다.

---

## 이 프로젝트의 전제

**2-stage 구조의 1차 게이트**다.

```
카메라 프레임 ──► [YOLO: VIN 스티커 위치 탐지] ──► 크롭 ──► [바코드 디코더] ──► 차량 식별
                        (이 저장소)                              (별도 시스템)
```

풀프레임을 디코더에 넣는 건 비싸서, YOLO 가 **ROI(스티커 영역)만 먼저 찾아** 넘긴다.

### recall 이 최우선인 이유 — 비용이 비대칭이다

| | 결과 | 비용 |
|---|---|---|
| **미탐 (FN)** | 차가 지나가버림. 디코더가 크롭조차 못 받음 | **영구 손실. 복구 불가** |
| **오탐 (FP)** | 디코더가 엉뚱한 크롭을 받아 디코딩 실패 → 버림 | 연산 약간 낭비. 피해 없음 |

디코더가 사실상 2차 정밀 필터 역할을 하므로, **precision 보다 recall 을 우선**한다.
배포 시 conf 를 기본값보다 낮춰 미탐을 더 줄이는 것도 정석이다.

## 워크플로우

### 1. 영상 → 학습후보 프레임

```bash
python scripts/prepare_frames.py --input <영상폴더> --output data/260619/frames_for_label
```

수만 프레임 중 대부분은 빈 화면이라 그대로 라벨링할 수 없다. 이 스크립트는:

1. **빈 화면 제거** — MOG2 배경차분으로 차량이 있는 프레임만
2. **근접 중복 제거** — dHash 로 거의 같은 프레임 버림 (차 한 대가 수십 프레임에 걸침)
3. **오버레이 제거** — 아래 "함정" 참고
4. **분류** — `detected/`(박스 있던 프레임) / `missed/`(차는 있는데 박스 없음 = 미탐 후보)

> PoC 시스템이 이미 스샷을 뽑아준 경우엔 이 단계를 건너뛰고 `<배치>/images/` 에 바로 넣으면 된다.

### 2. 사전 라벨 생성

```bash
python scripts/auto_label.py --batch data/260701
```

기존 모델로 추론해 `.txt` 를 만들어 두면 VisoLabel 에서 **박스가 그려진 상태로** 열려
검수만 하면 된다. 결과는 `<배치>/visolabel/`(이미지+txt 한 폴더) 와 `<배치>/labels/` 에 생성.

**conf 는 낮게 잡는다** (기본 0.2). 이유:
- 오탐은 학습에 안 들어간다 — 검수 때 클릭 한 번으로 지운다
- 미탐은 사람이 박스를 새로 그려야 하고(느림), **놓치면 "VIN 이 있는데 배경"으로 학습되어 recall 을 직접 깎는다**
- 즉 사전라벨에선 **과검출이 미검출보다 훨씬 싸다**

### 3. VisoLabel 검수 — 라벨링 기준

`<배치>/visolabel/` 폴더를 열어 검수한다. 규칙은 **하나**:

> **바코드 막대가 구분되어 디코딩될 법하면 라벨 O / 초점이 안 맞아 번진 smear 면 라벨 X(배경)**

- 기준은 **밝기가 아니라 선명도**다. 어두워도 막대 대비가 살아 있으면 라벨한다
  (Global Shutter 카메라는 어두워도 잘 읽힌다. 오히려 밝히면 노이즈가 증폭된다 —
  **CLAHE 같은 밝기 정규화를 하지 말 것**)
- 양방향 2카메라 구성에서 **반대편 차선 차량은 초점이 안 맞아 번진다** → 라벨 X.
  어차피 디코더가 못 읽고, 그 차량은 반대편 카메라가 자기 초점거리에서 잡는다
  (시스템 전체 recall 손실 0). 흐린 걸 라벨하면 헛디코딩만 늘고 라벨 노이즈로
  **선명한 것의 recall 까지 떨어진다**
- **일관성이 생명**이다. 어중간한 걸 어떤 건 치고 어떤 건 안 치면 학습이 무너진다.
  컷오프가 애매하면 **실제 디코더에 크롭을 넣어보고** 성공하는 최저 선명도를 기준으로 삼는 게 가장 정확하다

### 4. 세션 단위 배치

```bash
python scripts/prepare_split.py --src data/260701 --train-sessions s1,s2 --eval-sessions s3
```

**프레임을 랜덤 분할하면 안 된다.** 같은 차량이 여러 프레임·여러 카메라에 걸쳐 찍히므로
랜덤 분할하면 같은 차가 train 과 val 양쪽에 들어가 **성능이 가짜로 높게** 나온다.
반드시 **세션을 통째로** 갈라야 한다.

배경은 `--bg-ratio`(기본 2.0)로 **양성의 2배까지만** 넣는다. 배경이 과하면 모델이
"아무것도 없다"를 학습해 보수적으로 변하고 **recall 이 떨어진다**.

### 5. 학습

```bash
python scripts/train_vincode.py --base _model_/vincode_v4.pt --name v5   # 최신 모델에서 이어학습
python scripts/train_vincode.py --data data_field_only.yaml --name fieldonly   # A/B
python scripts/train_vincode.py --batch 4 --imgsz 1024                          # OOM 시
```

- **증분 학습보다 전체 재학습**을 권한다. 최신 모델에서 warm-start 하되 데이터는 전부 넣는다.
  이전 버전의 데이터가 학습셋에 그대로 있으므로 "이전 지식을 잊는" 문제는 생기지 않는다
- `val/test` 는 **배포 도메인만** 쓴다 → `best.pt` 가 실제 환경 기준으로 선택된다
- 같은 `--name` 이 있으면 자동으로 번호가 붙어 **기존 가중치를 덮지 않는다**

증강은 "배포 환경에서 **실제로 변하는 축**"만 켠다. 고정 카메라라 좌우반전·모자이크는
가짜 데이터고, 흑백이라 색조·채도 증강은 무의미하다. 자세한 근거는
`train_vincode.py` 주석 참고.

## 함정 (실제로 겪은 것들)

### 1. 오버레이가 픽셀에 구워져 있으면 학습이 오염된다

운영 중인 모델이 그린 **검출 박스가 영상/스샷에 burn-in** 된 경우가 있다.
그대로 학습하면 모델이 **"노란 사각형 = VIN"** 이라는 가짜 단서를 배운다.
배포 땐 그 사각형이 없으니 성능이 무너진다.

다행히 박스는 **얇은 외곽선**이라 inpaint 로 지워도 안쪽 내용물은 살아남는다.
`prepare_frames.py` 가 이 처리를 한다. 스샷을 직접 받은 경우에도 **반드시 확인할 것**.

### 2. 어두운 프레임에서 inpaint 가 화면을 뭉갠다

내용물이 흑백이라 "채도 있는 픽셀 = 오버레이"로 잡는데, **어두운 픽셀은 노이즈 때문에
채도가 가짜로 높게** 나온다. 채도만으로 마스크를 만들면 노출 낮은 영상에서
**화면의 80%가 오버레이로 오인**되어 inpaint 가 전부 뭉갠다.

→ 마스크에 **밝기(V) 조건을 반드시 함께** 건다 (`SAT_OVERLAY` + `VAL_OVERLAY`).

### 3. 데이터 검증은 반드시 전수로

샘플 한두 장만 보고 "깨끗하다"고 판단했다가 두 번 틀렸다.
오버레이 유무·마스크 비율 같은 건 **전 파일을 스캔해서** 통계로 확인할 것.

### 4. 파일명 충돌

세션마다 `v001_...` 처럼 번호가 리셋되는 경우, 한 폴더로 합치면 **덮어써서 사라진다**.
(실제로 358장 → 147장이 될 뻔했다.) 합칠 때 **세션 접두사**를 붙인다.
세션 정보는 4번 단계(세션 분할)에도 필요하다.

### 5. predict 에 리스트를 통째로 넘기면 OOM

`model.predict([...358장...], stream=True)` 는 `stream=True` 여도 **그 길이만큼 한 배치**로
묶어서 8GB GPU 가 터진다. `auto_label.py` 는 `--chunk`(기본 16) 단위로 나눠 넘긴다.

## 실험 기록

동일 test 셋(배포 도메인) 기준.

| 모델 | 학습 데이터 | precision | recall | mAP50 | mAP50-95 |
|---|---|---|---|---|---|
| v1 | v1(컬러)만 | 0.29 | 0.38 | 0.31 | 0.20 |
| v2 | v1 + 현장 | 0.68 | 0.75 | 0.77 | 0.67 |
| **v3** | v1 + 현장(확장) | 0.71 | **0.86** | 0.84 | 0.79 |
| v3.1 | 현장만 (v1 제외) | **0.91** | 0.72 | 0.87 | 0.80 |

- **v1 단독은 현장에서 쓸 수 없다**(recall 0.38). 도메인 적응이 핵심이었다
- **v3.1(현장만)은 precision 이 크게 오른다**(0.71 → 0.91). v1 의 컬러 도메인에서 온
  spurious 패턴이 사라진 효과. mAP 도 밀리지 않는다
- 그런데도 **배포는 v3 를 채택**했다. 미탐이 치명적인 구조라 recall 0.86 > 0.72 가 결정적이고,
  v3.1 의 정밀도 우위는 "오탐이 싼" 이 시스템에선 거의 쓸모없는 강점이기 때문
- v1 을 빼는 게 이득인지는 **용도에 따라 다르다**. 오탐 비용이 큰 시스템이라면 v3.1 이 낫다

### 시도했다가 접은 것

**같은 세션에서 프레임 재추출(2차 마이닝)** — 이미 추출한 세션에서 모델을 낮은 conf 로
다시 돌려 후보를 더 캐는 방식. 신규 수율이 **영상당 ~37장**(대부분 hard negative)에 그쳤다.
distinct 차량 통과 수가 세션당 수십 대로 한정되고 1차 추출이 이미 훑어간 탓이다.

→ **recall 을 실질적으로 올리려면 같은 세션 재활용이 아니라 새 촬영**(다른 날·조명·차종)이 답이다.
